# Internationalization

FinTrack's UI and API error messages are translatable. This is the
infrastructure from [ROADMAP.md](../ROADMAP.md) Phase 1: a real pipeline from
"a string in the source code" to "a string a translator can see and change",
plus a first pass of the highest-traffic screens (navigation, auth,
settings, account errors) actually wired through it. It is not a claim that
every string in the app is translatable yet - see
[What it deliberately does not do](#what-it-deliberately-does-not-do).

## What it does

- **Frontend**: `apps/web` uses [react-i18next](https://react.i18next.com/).
  Catalogs live at `apps/web/public/locales/<lang>/translation.json` and are
  fetched at runtime (`i18next-http-backend`, see `apps/web/app/i18n.ts`) -
  the same static-asset origin as `manifest.webmanifest` - rather than bundled,
  so a translation update ships without a frontend rebuild. Language is
  detected from `localStorage` (set by the language switcher in the top bar)
  falling back to the browser's `navigator.language`, and both catalogs are
  precached by the service worker (`apps/web/public/sw.js`) so the last
  language used still renders offline.
- **Backend**: `apps/api` uses [Django's gettext](https://docs.djangoproject.com/en/5.1/topics/i18n/translation/).
  `LocaleMiddleware` (`app/settings/base.py`) activates a language per request
  from the `Accept-Language` header; strings wrapped in `gettext`/`gettext_lazy`
  (validation errors, account-flow messages today) translate accordingly.
  Catalogs live in `apps/api/locale/<lang>/LC_MESSAGES/django.po`. `*.mo`
  files are compiled from those at Docker build time and again on every
  container boot (`entrypoint.sh`, and inline in `worker`/`beat`'s command in
  `docker-compose.yml`) so `make dev`'s bind mount - which shadows the image's
  build-time compile with the host's `.po`-only checkout - still has working
  translations.
- **Extraction tooling**: `pnpm --dir apps/web i18n:extract` (wraps
  [i18next-cli](https://github.com/i18next/i18next-cli), configured in
  `apps/web/i18next.config.ts`) scans `t()`/`useTranslation()` calls and syncs
  `public/locales/*/translation.json` - new keys get an empty placeholder in
  every non-English locale for a translator to fill in, and (per its default
  `removeUnusedKeys`) keys no longer referenced anywhere are dropped, so the
  catalogs don't accumulate dead strings the way the feature matrix used to
  (see Phase 0's `make feature-audit` fix). On the backend, the equivalent is
  `uv run manage.py makemessages -l en -l es` from `apps/api/`.
- **Two seed languages**: English (source) and Spanish, enough to prove
  switching actually works end to end rather than infrastructure nobody has
  exercised. The language switcher (`apps/web/app/components/language-switcher.tsx`)
  reads its list from `SUPPORTED_LANGUAGES` in `apps/web/app/i18n.ts`; the
  backend's equivalent is the `LANGUAGES` setting in `app/settings/base.py`.
  Both need a new entry (plus a `public/locales/<lang>/translation.json` and/or
  a `locale/<lang>/LC_MESSAGES/django.po`) for a language to go live - there is
  no other code to change.

## What it deliberately does not do

- **It does not translate the whole app yet.** Full coverage is a
  standing, incremental job for whoever's touching a given screen next, not
  something to do speculatively ahead of a translator asking for it. The
  parts wired up now - sidebar, top bar, command palette, settings shell,
  login/register, notification preferences, quick add, split transactions -
  are the highest-traffic, lowest-churn surfaces, chosen so the pipeline has
  real coverage to prove itself rather than one placeholder string.
- **It is not connected to a live Weblate project.** The two catalog formats
  (web JSON, API gettext) are exactly what Weblate expects out of the box -
  see [Wiring up Weblate](#wiring-up-weblate) for the two components it
  needs - but actually creating that project needs a Weblate account, which
  only the maintainer can decide where to run (hosted weblate.org, or
  self-hosted alongside the rest of the stack). Same shape as the Phase 0
  "Live demo instance" item: the machinery is built and the one remaining
  step needs somebody's account.
- **Machine-assisted, not machine-translated-and-shipped-blind.** The seed
  Spanish strings were written deliberately, but neither language has had a
  native speaker's editorial pass. Treat both as a starting point Weblate
  (and its contributors) will correct, not a finished translation.

## Adding a new translatable string

**Frontend:**

1. Pick (or add to) a namespaced key in `public/locales/en/translation.json`,
   e.g. `"settings.profile.saveProfile"`.
2. Use it: `const { t } = useTranslation(); t('settings.profile.saveProfile')`.
3. Run `pnpm i18n:extract` from `apps/web/` and commit the catalog diff. If
   you're adding a brand new key, write its English value directly into
   `translation.json` yourself (the extractor doesn't invent copy) - it exists
   to keep every locale's key set in sync and prune dead keys, not to draft
   English text for you.
4. Leave the new key's value empty (`""`) in every other locale - that's what
   marks it untranslated for Weblate. Do not paste English into a non-English
   catalog as a placeholder; empty is the correct "missing" state.

**Backend:**

1. Wrap the string: `from django.utils.translation import gettext_lazy as _`
   (use `gettext` instead of `gettext_lazy` only inside a function body where
   the request's active language is already known at call time - lazy is
   correct for anything evaluated at import/class-definition time, e.g. a
   serializer's `error_messages` or a model field's `help_text`).
2. From `apps/api/`, run:
   ```bash
   uv run manage.py makemessages -l en -l es
   ```
3. Fill in the new `msgstr` in `locale/es/LC_MESSAGES/django.po` (or leave it
   empty for Weblate to pick up) and commit both `.po` files. Never commit
   `.mo` - it's build output (`apps/api/.gitignore`).

## Adding a new language

1. Frontend: add `{ code: '<lang>', label: '<Native name>' }` to
   `SUPPORTED_LANGUAGES` in `apps/web/app/i18n.ts`, then create
   `apps/web/public/locales/<lang>/translation.json` - easiest by copying
   `en/translation.json` and translating the values (keys must match
   exactly). Add it to `APP_SHELL_FILES` in `apps/web/public/sw.js` if you
   want it precached for offline use.
2. Backend: add `("<lang>", "<Native name>")` to `LANGUAGES` in
   `apps/api/app/settings/base.py`, then run
   `uv run manage.py makemessages -l <lang>` from `apps/api/` and translate
   the generated `locale/<lang>/LC_MESSAGES/django.po`.
3. Both lists are maintained by hand in parallel - there's no shared config
   between the two apps to drive this from one place.

## Wiring up Weblate

There are exactly two catalog shapes in this repo, so this is two components
added by hand through the Weblate admin UI - the
[Component Discovery add-on](https://docs.weblate.org/en/latest/admin/addons.html#component-discovery)
is for repos with an open-ended, dynamically-named set of components (e.g. one
per plugin) and isn't needed here. Once you have a Weblate project (hosted or
self-hosted) with this repository added as its source:

1. **Web UI** component: file format `JSON nested structure file`, file mask
   `apps/web/public/locales/*/translation.json`, template
   `apps/web/public/locales/en/translation.json`, source language `en`.
2. **API** component: file format `GNU gettext PO file`, file mask
   `apps/api/locale/*/LC_MESSAGES/django.po`, new base
   `apps/api/locale/en/LC_MESSAGES/django.po`, source language `en`.
3. Push branch: `main` on both, with Weblate opening pull requests for
   translation updates - review them like any other PR.

See [CONTRIBUTING.md](../CONTRIBUTING.md) for the general PR workflow, and the
[How to help](../ROADMAP.md#how-to-help) table in the roadmap - translation is
listed there as the fastest path to contributor status once this is live.
